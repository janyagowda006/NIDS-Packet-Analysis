# Network Intrusion Detection System (NIDS) with Packet Analysis

An educational Network Intrusion Detection System designed to capture, parse, analyze, and detect anomalous network traffic in an isolated laboratory environment.

## Core Principle

> **"Analyze first, detect second, explain every alert."**

Every security alert generated by this system must provide an explainable technical justification, including protocol context, observed metrics, evaluation windows, and rule threshold boundaries.

## Technology Stack

- **Core Language**: Python 3.13
- **Packet Capture & Dissection**: Scapy
- **Traffic Analysis & Connection State**: Python stateful analysis engines
- **Storage**: SQLite
- **Visualization & Triage**: Streamlit
- **Testing & Verification**: pytest

## Development Status

- **Current Phase**: **Phase 11 — Streamlit Dashboard**
- **State**: Core packet acquisition, protocol normalization, stateful traffic analysis, detection engines (Phases 5–9), SQLite alert persistence (Phase 10), and Streamlit presentation dashboard (Phase 11) implemented and verified with 230 unit and integration tests.

## Packet Capture Architecture

The capture layer (`backend/capture/`) decouples packet acquisition from downstream protocol parsing and threat detection, supporting three capture modes:

1. **Live Interface Capture (`PacketCaptureEngine.capture_live`)**:
   - Captures live network traffic using Scapy.
   - Supports configurable interface selection, packet count limits, capture timeouts, and Berkeley Packet Filters (BPF).
   - **Environment Requirement**: On Windows hosts, live capture requires the [Npcap driver](https://npcap.com/) installed with *"WinPcap API-compatible Mode"*. On Linux VM environments (Kali / Ubuntu), raw sockets (`AF_PACKET`) are used natively with appropriate permissions.
   - Fails gracefully with `DriverMissingError` if the required packet capture driver is absent.

2. **Offline PCAP Replay (`PacketCaptureEngine.read_pcap` & `stream_pcap`)**:
   - Safely parses and streams packets from local `.pcap` or `.pcapng` files.
   - Operates purely offline without requiring Npcap or elevated privileges, enabling reproducible laboratory analysis and grading.

3. **Synthetic / Mock Stream (`PacketCaptureEngine.capture_mock` & `stream_mock`)**:
   - Ingests in-memory Scapy packets for deterministic, isolated unit testing without physical network transmission or driver dependencies.

## Network Interface Discovery

The `backend/capture/interfaces.py` module discovers available adapters across Windows and Linux:
- Normalizes interface details into structured `NetworkInterface` objects (Name, Description, MAC, IPv4, Status, Loopback flag, GUID).
- Safely handles interfaces with missing IPv4, missing MAC, or unassigned addresses.
- Detects whether layer-2 capture drivers are present via `is_pcap_driver_available()`.

## Packet Parsing and Normalization

The parsing layer (`backend/parser/`) transforms raw Scapy packets into an immutable, strongly-typed `NormalizedPacket` model:

- **Decoupled Architecture**: `PacketDissector.parse(packet)` consumes raw packets from live capture, PCAP replay, or synthetic test streams, producing normalized data structures consumed by downstream traffic analysis (Phase 4) and detection rules (Phases 5–9).
- **Supported Protocols**:
  - **Ethernet**: Source & destination MAC addresses.
  - **IPv4 / IPv6**: Source & destination IP addresses.
  - **TCP**: Source & destination ports, deterministic flag formatting (`SYN`, `ACK`, `FIN`, `RST`, `PSH`, `URG`, `ECE`, `CWR`), raw flag strings.
  - **UDP**: Source & destination ports.
  - **ICMP**: Message types (e.g., Echo Request Type 8, Echo Reply Type 0) and codes.
  - **ARP**: Operation codes (Request op=1, Reply op=2), sender/target MAC and IP addresses.
  - **DNS**: Query domain name (FQDN), query type (A, AAAA, PTR, TXT).
  - **DHCP**: Message types (discover, offer, request, ack).
  - **HTTP**: Request method (GET, POST, etc.), Host header, and URI path (extracted from payload headers without full payload retention).
- **Fault-Tolerant Dissection**: Packets with missing layers, unknown protocols, or malformed payloads never crash the capture or parsing pipeline; they return a partially populated `NormalizedPacket` with `protocol="UNKNOWN"` and raw lengths intact.

## Traffic Analysis and Connection Tracking

The traffic analysis layer (`backend/analysis/`) consumes `NormalizedPacket` streams to maintain connection sessions, sliding time-window history, and cumulative traffic metrics:

- **Bidirectional Connection Tracking**:
  - The `FlowKey` abstraction normalizes endpoints into a canonical representation, ensuring forward (A->B) and reverse (B->A) packets map to the same logical `FlowRecord`.
  - For IP/transport traffic, endpoints are ordered deterministically by `(IP, Port)`.
  - Supports portless protocols including ICMP and ARP.
- **TCP Connection Lifecycle**:
  - Tracks TCP handshake and termination progression: `NEW`, `SYN_SENT`, `SYN_RECEIVED`, `ESTABLISHED`, `CLOSING`, `CLOSED`, and `RESET`.
  - Records granular state flags: `syn_seen`, `syn_ack_seen`, `ack_seen`, `fin_seen`, and `rst_seen`.
- **Cumulative Traffic Metrics**:
  - `TrafficStatistics` aggregates total packet counts, total byte volumes, protocol distributions (TCP, UDP, ICMP, ARP, DNS, HTTP), and sets of unique source/destination IPs and ports.
- **Sliding Time-Window Support**:
  - `get_packets_in_window()` and `get_flows_in_window()` provide time-windowed queries across past traffic, enabling future detection modules (Phases 5–9) to evaluate rate thresholds over configurable durations (e.g., connection attempts per second).
- **Reset and Reuse**:
  - `TrafficAnalyzer.reset()` clears all tracked sessions, buffers, and statistics to ensure clean state transitions between capture sessions.

## Streamlit Security Dashboard (Phase 11)

The presentation layer (`frontend/`) visualizes detection events, severity statistics, and explainability evidence managed by `AlertManager` and SQLite storage:

- **Launch Command**:
  ```bash
  streamlit run frontend/dashboard.py
  ```
- **Capabilities**:
  - **Summary Metrics**: Real-time totals for active alerts, new alerts, high/critical threats, and resolved events.
  - **Analytics Charts**: Visual distributions of severity levels, alert types, and triage status states.
  - **Filtered Triage**: Dynamic multi-criteria filtering across severity, threat type, source IP, and status.
  - **Explainability Evidence**: Deep inspection of individual alerts, displaying technical descriptions, trigger rationales, and machine-readable JSON telemetry.
  - **Alert Triage Lifecycle**: In-place status updates (`NEW` → `ACKNOWLEDGED` → `RESOLVED`) using `AlertManager`.
